# Local checks

#### When to use this file

These blocks are local additions to the upstream class files in `classes/`. Each one names a concrete pattern to look for in source or configuration, the trust boundary it crosses when it is real, and a bounded check with dummy data that settles it. Most of them narrow an upstream class to the exact files and settings where that class shows up in JavaScript, Python, GitHub Actions, Docker, and Claude Code projects; the block says which upstream class it extends.

Select a block the same way as an upstream one: because recon found the boundary it describes, never because a file name or dependency appears. When you select a block that extends an upstream class, also select that upstream block, so the hunter receives the general discipline and the concrete pattern together. Block references take the form `local-classes.md#<name in bold>`, for example `local-classes.md#Privileged trigger that runs pull request code`. A hit in `ci-surface.json` (recon.md, Signals) seeds or prioritizes a unit for the matching block; it is never a finding by itself.

## Core discipline (include in every agent prompt that receives a block from this file)

```
- A pattern match is a lead. A finding still needs a lower-trust principal, a crossed boundary, and a bounded observed result, exactly as for the upstream classes.
- The owner is auditing their own code to fix it. Every check uses dummy principals, dummy secrets, local fixtures, and loopback services. Nothing here contacts a deployed system, a registry, a CI provider, or a cloud account, and nothing here installs a tool.
- Host settings decide many of these results: branch protection, environment reviewers, fork-approval policy, registry scopes, cloud trust policies, and which build mode deploys. When one of them is decisive and not in source, the record is `needs_validation` with the setting the owner should look at.
- A missing setting with no reachable principal and effect (no `permissions:` block, a container running as root, a source map with nothing private in it) is a hardening note.
- Quote expression names, setting names, and variable names; never quote a secret value. Use the redacted preview from `secret-sweep.json`.
```

## CI and release (extends `classes/SUPPLY-CHAIN-AND-RELEASE.md`)

**Privileged trigger that runs pull request code**
Extends `SUPPLY-CHAIN-AND-RELEASE.md#Untrusted code in a privileged workflow`. A workflow triggered by `pull_request_target`, `workflow_run`, or `issue_comment` runs in the base repository's context, with its secrets and a `GITHUB_TOKEN` that can write unless narrowed. Look for steps in such a workflow that then check out or execute contributor code: an `actions/checkout` `ref:` built from `github.event.pull_request.head.sha`, `head.ref`, `github.head_ref`, or `refs/pull/<n>/...`; `gh pr checkout` or `git fetch origin pull/...`; or a download of an artifact produced by the triggering run that is then executed, sourced, unpacked over the workspace, or read as configuration. Once contributor code is on disk, any later step that runs install hooks, build scripts, tests, linters, or an action that reads repository configuration runs that code. The boundary is a fork contributor gaining the base repository's secrets or write token. Local check: from the workflow file alone, list each step in order with the ref it reads, whether contributor-controlled files exist on disk at that point, and the secrets and token permissions in scope. Whether a protected environment or fork-approval setting gates the job is a host fact; when it decides the result, the record is `needs_validation`.

**Untrusted expression in a shell or script step**
Extends `SUPPLY-CHAIN-AND-RELEASE.md#Workflow command and expression confusion`. GitHub expands `${{ }}` before the shell or script sees the text, so an untrusted value placed inside `run:` or inside `actions/github-script`'s `script:` becomes code. Untrusted sources include `github.event.*` text fields (issue and comment bodies and titles, pull request titles and bodies, branch names, commit messages, author names), `github.head_ref`, and `inputs.*` on workflows other principals can trigger. Numeric IDs and commit SHAs are not attacker-chosen text. Also look for untrusted values written to `$GITHUB_ENV`, `$GITHUB_PATH`, or `$GITHUB_OUTPUT`: a line written to `GITHUB_ENV` sets an environment variable for every later step in the job, including variables that change what a program loads at startup, and an output can carry the value into a later `run:`. The safe pattern passes the value through a step-level `env:` entry and quotes it in the shell. The boundary is whoever can set the text (an issue author, a fork branch name) running commands with the workflow's token and secrets. Local check: copy the `run:` body into a scratch script, substitute a harmless marker value for the expression the way GitHub would (for example a title containing `"; echo MARKER; #`), and run it with an empty environment to show the marker executes; the observed result is the marker line, nothing more.

**Workflow token and secret scope**
Extends `SUPPLY-CHAIN-AND-RELEASE.md#Automation identity overreach`. Look for workflows with no top-level `permissions:` block (the token then gets the repository's default, which is a host setting), `permissions: write-all`, secrets placed in workflow-level or job-level `env:` where every step including third-party actions can read them, and secrets passed through `with:` to actions outside the owner's organization. A specific case: `actions/checkout` leaves the token in `.git/config` unless `persist-credentials: false` is set, so a later `actions/upload-artifact` with `path: .` or the workspace root publishes that token inside the artifact to anyone who can download artifacts. Missing narrowing alone is hardening; it becomes a candidate when a lower-trust input can reach a step holding the broad token or secret (combine with the two blocks above), or when the artifact path includes `.git`. Local check: in a scratch fixture repository, reproduce the checkout and the upload path selection with a dummy token string, and list the files the upload glob would include.

**Cloud identity federation from CI**
Extends `CLOUD-AND-DEPLOYMENT.md#Cross-account or cross-tenant role confusion`. Infrastructure code (Terraform, CloudFormation, Pulumi, gcloud or az scripts) that trusts GitHub's OIDC tokens must bind the token's `sub` claim to the exact repository and to a branch, tag, or environment. Look for conditions such as `repo:org/*`, `repo:org/repo:*`, a `StringLike` on `sub` with a wildcard, an audience check without a subject check, or no condition at all. On the workflow side, look for `id-token: write` on workflows triggered by `pull_request`, `pull_request_target`, or `issue_comment`, where a contributor's run can mint a token. The boundary is another repository, a fork's run, or an unprotected branch assuming the deployment role. Local check: evaluate the trust condition in source against a list of dummy `sub` values (`repo:org/other:ref:refs/heads/main`, `repo:org/repo:pull_request`, `repo:org/repo:ref:refs/heads/feature`) and record which ones match. The live role's policy may differ from source; when it decides the result, the record is `needs_validation`.

**Coding agent in CI driven by untrusted text**
Extends `AI-AND-LLM.md#Indirect injection through retrieved or ingested content`. A workflow step runs a coding agent with tools (`claude -p`, the Claude Code GitHub action, `codex exec`, or another model with shell, file-write, or network tools) on an `issue_comment`, `issues`, `pull_request_target`, or `discussion` trigger, and the prompt includes text the commenter or author controls: the comment body, the issue title, a diff, or files from the pull request. A model cannot be relied on to ignore instructions in that text, so the controls that count are deterministic ones: who may trigger the step (author association or an allowlist checked before the agent runs), which tools the agent is allowed, and which secrets and token permissions exist in the job. The boundary is an outside commenter directing an agent that holds the repository's token, secrets, or write tools. Local check: list the trigger, the trigger gate, the allowed tools from the step's arguments or settings, and the secrets and permissions in scope. Do not run the agent against a crafted prompt; the source facts settle the finding.

## Dependencies (extends `classes/SUPPLY-CHAIN-AND-RELEASE.md`)

**Internal package name resolvable from a public registry**
Extends `SUPPLY-CHAIN-AND-RELEASE.md#Dependency source and namespace confusion`. Look for unscoped dependency names that read as internal (company or product prefixes, `-internal`, `-shared`, `-common`), scoped names whose scope has no `@scope:registry=` line in any `.npmrc`, pip configuration using `--extra-index-url` (pip picks the highest version across all indexes, so a public package with the same name and a higher version wins), lockfile `resolved` URLs pointing at hosts other than the expected registry, git or tarball URLs as dependency specs, lockfile entries with no `integrity`, and container images named without a registry host (`FROM myorg-base` resolves against Docker Hub). The boundary is a stranger who publishes that name on the public registry getting their code into the owner's build. Local check: from the lockfile and configuration alone, list for each such package the registry a clean install would query. Whether the name is already taken on the public registry is an owner check (`npm view <name>` or the registry website, run by the owner); never publish or reserve a name as part of the audit.

**Install-time code in the repository and in CI**
Extends `SUPPLY-CHAIN-AND-RELEASE.md#Mutable and unbound build inputs`. Look at the repository's own `preinstall`, `install`, `postinstall`, and `prepare` scripts in every `package.json`: one that downloads and runs remote content, or reads environment variables and sends them anywhere, runs on every install by every contributor and CI job. Then look at CI jobs that hold secrets and run `npm install` (which can rewrite the lockfile and resolve new versions) instead of `npm ci`, or install without `--ignore-scripts`, so every dependency's install hooks run beside those secrets. The boundary is a dependency author, or whoever controls the remote URL, executing code with the CI job's secrets. Local check: list each lifecycle script with the URLs and environment variables it references, and each install command in a job with the secrets in scope at that step. Never run the install scripts.

**Dependency name close to a popular package or not yet real**
Extends `SUPPLY-CHAIN-AND-RELEASE.md#Dependency source and namespace confusion`. Look for dependency names one edit away from a widely used package (a swapped, missing, or doubled letter; `-js` or `.js` added or dropped; a hyphen moved), and for names that no other file in the repository imports or that appear only in AI-generated code or docs, which may have been invented by a model and later registered by someone else. The boundary is the owner of that look-alike name running code in the build. Local check: list the suspect names with the popular name each resembles and every file that imports it. Whether the package exists, who publishes it, and how new it is are registry facts, so the record is `needs_validation` with the owner check, unless the lockfile already shows the look-alike was installed.

## Claude Code configuration (no upstream class)

Claude Code reads `.claude/settings.json`, `.claude/settings.local.json`, `.mcp.json`, and `.claude/skills/` from the repository it opens. Anything committed there runs or grants authority on every contributor's machine and in every CI job that starts Claude Code in the repository.

**Hook command built from tool input**
A hook in `.claude/settings*.json` receives JSON about the tool call on standard input, including file paths, file contents, and shell commands the model chose. Look for hook commands or the scripts they call that pass those values into a shell unquoted, through `eval`, through `$(...)` built from file content, or into `sh -c` strings. The model's tool input is shaped by whatever text it read, including a pull request or web page, so the boundary is that text's author running commands on the developer's machine outside Claude Code's permission prompts. Local check: run the hook script with a dummy JSON payload on standard input whose `file_path` holds a harmless marker such as `a$(echo MARKER).txt`, in the empty-environment template, and record whether the marker executes.

**Permissions that remove the prompt**
Look for committed `permissions.allow` entries of `Bash`, `Bash(*)`, or broad prefixes such as `Bash(curl:*)` or `Bash(node:*)`; `permissions.defaultMode` set to `bypassPermissions`; and `enableAllProjectMcpServers: true`, which starts every server in `.mcp.json` without asking. These are settings, not code, so they become findings only when combined with a path for lower-trust text to reach the model (a skill or workflow that reads issues, pull requests, or web pages) in the same configuration. Otherwise they are hardening notes. Local check: list each broad entry with the file that sets it and any skill, hook, or workflow in the repository that feeds outside text to a session using it.

**MCP server launched from an unpinned or remote source**
Look in `.mcp.json` for servers started with `npx -y <package>` or `uvx <package>` without an exact version (each start fetches whatever the registry serves), servers reached at a remote URL, and literal secret values in a server's `env` or `args` instead of a reference to an environment variable. The boundary for an unpinned package is its publisher, or anyone who takes over the name, running code on every contributor's machine; for a committed secret, it is anyone who can read the repository. Local check: list each server with its launch command, whether the version is exact, and the names (never values) of secret-looking `env` keys and arguments.

**Skill with broad tools that reads outside text**
Look for skills in `.claude/skills/` whose `allowed-tools` frontmatter grants `Bash`, `Write`, or `Edit` without narrowing and whose instructions read issue bodies, pull request text, review comments, web pages, or downloaded files. The skill then runs with those tools while the model holds text another person wrote. The control that counts is a deterministic one: narrower tools, a confirmation step the text cannot answer, or a separate read-only agent for the outside text. Local check: list the skill, its tools, and each place its instructions bring in outside text.

## Deployment and client (extends `classes/CLOUD-AND-DEPLOYMENT.md` and `classes/WEB-PROTOCOL-AND-AUTH.md`)

**TLS verification turned off**
Extends `CLOUD-AND-DEPLOYMENT.md#Security-control precedence drift`. Look in code, Dockerfiles, CI, scripts, and committed `.env*` files for `NODE_TLS_REJECT_UNAUTHORIZED=0`, `rejectUnauthorized: false`, `strictSSL: false`, `strict-ssl=false`, `verify=False` in Python HTTP clients, `InsecureSkipVerify: true` in Go, `curl -k` or `--insecure`, `wget --no-check-certificate`, `git config http.sslVerify false`, `GIT_SSL_NO_VERIFY`, and pip `--trusted-host`. The boundary is a network attacker between this process and its peer reading or changing traffic that carries credentials or code. Establish which path is active (a test-only file or a development flag is not production) and what travels over the connection. Local check: read the code path that selects the option and show which build or environment mode enables it; do not stand up an interception proxy against a real host.

**Client bundle carrying source maps or secrets**
Extends `WEB-PROTOCOL-AND-AUTH.md#API-key exposure and unsafe transport`. Look for production source maps (`productionBrowserSourceMaps: true` in Next.js, `build.sourcemap` in Vite, `devtool: 'source-map'` in a production webpack config, committed `*.map` files in build output) and for secret-looking variables with a public prefix (`NEXT_PUBLIC_*`, `VITE_*`, `REACT_APP_*`, `EXPO_PUBLIC_*`), which bundlers inline into JavaScript every visitor downloads. A source map of public client code is low at most; it matters when it exposes secrets, server-only code, or internal endpoints the client never calls. A public-prefixed variable matters when its value is a secret the server should hold (a service-role key, a payment secret key, a signing secret), not a publishable key designed for browsers. Local check: build with the project's own build command in the exec tree with dummy values for the variables, then search the output for the dummy values and for `.map` files.

**Dockerfile that bakes in secrets or remote code**
Extends `SUPPLY-CHAIN-AND-RELEASE.md#Build-context inclusion` and `SUPPLY-CHAIN-AND-RELEASE.md#Mutable and unbound build inputs`. Look for `ARG` or `ENV` carrying secret-looking names (both persist in image metadata or layers that anyone with the image can read; BuildKit `--mount=type=secret` does not), `ADD <url>` and `curl ... | sh` or `wget ... | sh` during the build (unpinned remote code in the image), `COPY . .` with a `.dockerignore` that misses `.env*` or key files, and images that never switch away from root. Root alone is a hardening note unless the container's own threat model depends on it. The boundary for a baked secret is anyone who can pull the image; for remote code, whoever controls the URL. Local check: from the Dockerfile and `.dockerignore`, list which instructions carry which names and which local files the build context would copy; do not build or pull images.

## Web, API, and auth (extends `classes/ATTACK-CLASSES.md` and `classes/WEB-PROTOCOL-AND-AUTH.md`)

**Client-supplied price, total, or currency**
Extends `ATTACK-CLASSES.md#Business logic`. Look for checkout, order, invoice, or subscription handlers that read `price`, `amount`, `total`, `subtotal`, `discount`, `tax`, `shipping`, `currency`, or `quantity` from the request and pass them to the payment provider or the order record instead of recomputing them from server-side catalog and tax data. Also look for currency taken from the request while the amount is computed in another currency, and for negative or fractional quantities that reduce a total. The boundary is a customer paying less than the server's own price for goods or credit. Local check: call the handler or its pure pricing function with a dummy cart and a request total lower than the catalog price, with the payment client mocked, and record the amount sent to the mock.

**Refund larger than the payment**
Extends `ATTACK-CLASSES.md#Business logic`. Look for refund and return logic that computes the amount per order rather than per returned item, allows several partial refunds whose sum exceeds the captured amount, refunds an amount recomputed from current prices rather than the price paid, or sends the refund to a method other than the original one (store credit, a gift card, or a newly added card) where that credit can be transferred or cashed out. The boundary is a customer receiving more than they paid. Local check: run the refund function against a dummy order with two items, return one item twice or return both after a discount, and record the total refunded against the total paid.

**Coupon and credit rules that do not hold under repetition**
Extends `ATTACK-CLASSES.md#Business logic`. Look for single-use coupons marked used in a separate step after the order is placed (two concurrent checkouts both pass the check), stacking rules that let discounts exceed the total and turn the negative balance into account credit, and codes normalized differently where they are applied and where uniqueness is checked (case, whitespace, Unicode width, or a trailing character). The boundary is a customer using one coupon more often than intended, or creating credit. Local check: against a local database with a dummy coupon, run two redemptions released together by one barrier and record attempts versus successes; or apply the normalized and raw forms of one code and record whether both succeed.

**One-time code with no attempt limit**
Extends `WEB-PROTOCOL-AND-AUTH.md#Password reset and broader recovery` and `WEB-PROTOCOL-AND-AUTH.md#Step-up binding and bypass`. Look for OTP, two-factor, email verification, and login-code checks without a per-code or per-account attempt counter that invalidates the code, and for limits counted per HTTP request when one request can carry many attempts: a GraphQL array batch, several aliases of the same mutation in one query, or a bulk endpoint. A six-digit code with a per-request limit and 100 aliases per request is checked 100 times per counted attempt. The boundary is someone with the first factor, or only the account identifier, completing verification without the code. Local check: send one local request with several aliased verification attempts using wrong codes and one right dummy code, and record how many attempts the counter recorded.

**GraphQL field resolver without the parent's authorization**
Extends `ATTACK-CLASSES.md#Access control` and `PROTOCOLS-RPC-AND-MESSAGING.md#Per-item and streaming authorization gaps`. Look for authorization checked only in root query resolvers (`order(id)` checks ownership) while nested field resolvers load related objects by ID without checking again (`order.customer.paymentMethods`, `user.organization.members`), and for types reachable through more than one path where only one path is guarded, including `node(id:)` lookups. The boundary is a user reading another user's or tenant's objects through a relation. Local check: run the resolver against a local schema with two dummy users, query a nested relation from an object the first user may read into an object owned by the second, and record the returned fields.

**Upload accepted by name or type but not by content**
Extends `ATTACK-CLASSES.md#Resource and file handling`. Look for upload handlers that check only the extension, only the client-sent `Content-Type`, or only magic bytes, and that store files under the web root, in a bucket served from the application's own origin, or with the original name. An SVG or HTML file served same-origin runs script in the application's origin, and a file in an executable directory may run on the server. The boundary is an uploader running script in other users' sessions or code on the server. Local check: upload a dummy SVG containing a harmless script marker to a local instance, fetch it back from the stored location, and record the response `Content-Type`, `Content-Disposition`, and whether the file is served from the application origin.

**XML parser that resolves external entities**
Extends `ATTACK-CLASSES.md#Injection` and `ATTACK-CLASSES.md#Resource and file handling`. Upstream mentions safe XML parsing only for SAML. Look for any XML parser that accepts input from a lower-trust principal with DTDs, external entities, or XInclude enabled: Java `DocumentBuilderFactory` or `SAXParserFactory` without the feature flags that disable them, Python `lxml` with `resolve_entities=True` or `load_dtd=True`, PHP `LIBXML_NOENT`, .NET `XmlResolver` set, and libraries that parse SVG, `.docx`, `.xlsx`, `.pptx`, RSS, SOAP, or SAML. Office files and SVG are XML even when the feature calls them images or documents. The boundary is the uploader reading local files or reaching internal URLs through the parser. Local check: parse a dummy XML file whose external entity points at a scratch file you created, and record whether the scratch file's marker text appears in the parsed output.

**Two layers reading different values from one request**
Extends `PROTOCOLS-RPC-AND-MESSAGING.md#Message boundary and canonicalization disagreement`, here for HTTP query strings and bodies. When a key appears twice (`?role=user&role=admin`), frameworks disagree: Express's `qs` returns an array, Flask's `request.args.get` returns the first value, PHP keeps the last, and many proxies and WAF rules read the first. Arrays and objects cause the same split: a validator that checks `typeof x === "string"` on one copy while the handler reads `x[0]`, or a JSON schema that validates a top-level field while the handler reads the same name from a nested object. Look for a check in one layer (middleware, gateway, signature verification, validator) and use in another that parses independently. The boundary is a request that passes the check with one value and acts with another. Local check: run both layers' parsers on the same dummy query string or body in one script and record the value each one returns.

**Response serializing fields the client never shows**
Extends `DATA-ISOLATION-AND-LIFECYCLE.md#Analytics, logs, traces, and diagnostics as alternate readers` for API responses. Look for handlers that return whole ORM objects or `SELECT *` rows (`res.json(user)`, `return model.to_dict()`, default serializers) where the client uses a few fields: password hashes, reset tokens, other users' email addresses, roles, internal flags, or tenant IDs travel with every response even though no screen displays them. The boundary is the requesting user reading fields about themselves or others they are not meant to see. Local check: call the handler with a dummy record that has every sensitive column filled with marker values, and list the markers present in the response.

**Opaque cursor or global ID trusted as authorization**
Extends `ATTACK-CLASSES.md#Access control`. Look for pagination cursors and Relay-style global IDs that are only base64 of an offset, a primary key, or `Type:id`, where the server decodes them and uses the result directly in a query without re-applying the caller's filter. Changing the decoded offset or ID then reaches rows outside the caller's result set, and changing `Type` can load an object through a resolver meant for another type. The boundary is a user reading records outside their own scope. Local check: decode a cursor from a local dummy response, change the ID or offset to one owned by a second dummy user, re-encode it, and record what the handler returns.

**Refresh token without rotation or binding**
Extends `WEB-PROTOCOL-AND-AUTH.md#Session fixation and invalidation`. Look for refresh endpoints that accept an expired refresh token, accept a refresh token issued to another client or session, issue a new access token without rotating the refresh token, or rotate it without detecting reuse (when an old refresh token is presented after rotation, the whole token family should be revoked). The boundary is someone holding a leaked or old refresh token keeping access after the user logs out or the token expires. Local check: against a local instance with a dummy account, refresh once, then present the first refresh token again, and record whether it succeeds and whether the second token still works afterwards.

**URL fetcher with no scheme allowlist**
Extends `ATTACK-CLASSES.md#Resource and file handling`. Upstream covers SSRF through hosts, redirects, and DNS. Look also at the scheme: fetchers built on libcurl bindings, `urllib`, Java `URL`, or generic "open URL" helpers accept `file:`, `gopher:`, `dict:`, `ftp:`, or `jar:` unless the code allows only `http:` and `https:`, and some follow a redirect from `https:` to another scheme. The boundary is a user who supplies a URL reading local files or speaking raw protocols to internal services. Local check: call the fetch function with a `file:` URL pointing at a scratch file you created and record whether its marker text comes back.

## Universal moves (apply across the above)

- Read the configuration the way the runner reads it: GitHub expands expressions before the shell runs, bundlers inline public variables at build time, and Docker records `ARG` and `ENV` in image metadata. Name the step where the untrusted value becomes code or the secret becomes readable.
- For every CI and agent block, list who can trigger the workflow or session, what runs before the first deterministic gate, and which secrets, tokens, and tools are in scope at each step.
- For every web block, run the server's own function with two dummy principals and compare what each one can read, pay, refund, or redeem.

## Validation rules (apply before reporting ANY finding from this file)

1. Name the lower-trust principal (fork contributor, commenter, package publisher, customer, uploader), the value or action they control, the control that should stop it, and the boundary result.
2. A configuration hit with no reachable principal, or a setting whose effect depends on host policy not in source, is a hardening note or `needs_validation`, never `confirmed`.
3. Every local check uses dummy values, scratch files, mocked payment and network clients, and loopback services. A check that would need a CI run, a registry query, a cloud call, or an image pull becomes an owner check in `validation_plan`.
4. For race, batch, and repetition checks, record the schedule or barrier, attempts versus successes, and the exact state change.
5. Return `confirmed` only with the complete source path and the bounded observed result. Return `needs_validation` naming the exact host setting, registry fact, or deployed configuration the owner should look at.
