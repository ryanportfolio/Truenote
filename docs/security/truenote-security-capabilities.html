Truenote security architecture

Security controls Truenote has today

How Truenote limits access, screens content and AI data paths, keeps answers tied to citations, protects the browser session, records security events, and checks every release. Each item names the evidence behind it.

Layered controls, tested at their boundaries

Truenote applies access limits on the server before retrieval, screens uploads and AI requests for sensitive data, refuses to answer without valid citations, restricts browser requests to its own origin, and hash-chains security events. This page includes only safeguards that have completed repository evidence or a recorded check of the hosted service, and each section states which.

Verified safeguards

VerifiedRepository tests on the October 9, 2026 main branch

“Verified” here means the named repository tests passed. Each card states which tests. Tests prove the code paths they exercise; settings on the hosted service are covered in the next section.

01

Program and clearance isolation

Every retrieval query and document read is limited in SQL to the signed-in user's program and clearance level. Saved conversations keep the citation excerpts a user was already shown, scoped to that user and program, even if their clearance is later lowered. Only super users can switch programs, one program per request.

Authorization unit tests passed

02

Role-based administration

Five roles (super user, senior manager, manager, supervisor, CSR) are enforced on every signed-in API route. Supervisors see only their own team. Only a super user can grant the super-user role.

Role and team-scope tests passed

03

Controlled content activation

Uploads must pass a file-type allowlist, a file-signature check, a 20 MB size limit, an EICAR test-file check, sensitive-data screening, source approval, and parsing. Private keys, AWS and OpenAI keys, Social Security numbers, and payment-card numbers quarantine the upload. Only senior managers and super users activate content; their own uploads activate once these checks pass. An external malware scanner can be connected; none is enabled on truenote.org today.

Activation and screening tests passed

04

Hybrid retrieval boundary

Vector, full-text, typo-tolerant, and neighboring-passage queries each apply the program, clearance, and lifecycle filters in SQL. Reranking only reorders results that already passed those filters.

Scope-filter unit tests passed

05

Answer-route retention policy

Each answer and query-rewrite request asks OpenRouter for Zero Data Retention, denies data collection, pins one model host, and turns off OpenRouter's own fallback. If a route fails, Truenote tries the next route on a fixed allowlist; administrators cannot add routes outside it.

Routing tests passed

06

Pre-provider input firewall

Deterministic patterns for private keys, AWS and OpenAI keys, US Social Security numbers, payment-card numbers (digits separated only by spaces or hyphens), email addresses, structured phone numbers, and IP addresses are redacted before text is sent for embedding, reranking, answer generation, query rewriting, or evaluation scoring. Uploaded files reach the document parser before this screen runs.

Provider-payload tests passed

07

Cite or refuse

An answer with missing, malformed, unknown, or out-of-range citations becomes a refusal. Fees, dates, counts, and identifiers written as numbers must appear in an excerpt the sentence cites, or in one the answer cites when the sentence has no citation. Answers containing sensitive data are refused.

Generation tests passed

08

Citation receipts

Each answer stores an ordered snapshot of its sources with document version and anchor context. Stale anchors are rejected, and revoked or deleted versions are dropped from history when version status can be read.

Citation tests passed

09

Browser request defense

Browser requests that change data must come from Truenote's own origin. The Origin and Fetch Metadata headers are checked, and foreign, opaque, malformed, cross-site, and sibling-origin requests are rejected. Requests that send neither header, such as non-browser API clients, pass this check and still need a valid session.

Browser-security tests passed

10

Redacted diagnostics

Structured error handling removes credentials, complete private keys, Social Security numbers, and payment-card values from covered diagnostic paths.

Redaction tests passed

11

Bounded provider failure

Each provider call has a deadline, a retry cap, and cancellation. The ask path as a whole has its own deadline and returns the standard refusal when it expires.

Failure-path tests passed

12

Workload limits

Asks have per-user and per-program limits, and document uploads have per-user limits. Both are stored in PostgreSQL, so they hold across server instances. Administrative routes have their own per-user limits.

Rate-limit tests passed

13

Evaluation integrity

Evaluation tests cover retrieval and reranking failure attribution, citation scoring, refusal questions, faithfulness, durable queue recovery, and separate pass rates for held-out questions.

Evaluation tests passed

Hosted service settings

VerifiedChecked on truenote.org, October 9, 2026

These settings were read from the live service's responses.

HTTPS only

Plain HTTP redirects to HTTPS. Strict-Transport-Security is set for two years with includeSubDomains and the preload directive; truenote.org is not yet on browser preload lists.

Content Security Policy

Scripts run only with a per-request nonce under strict-dynamic, Trusted Types are required, plugins are blocked, and no site can frame Truenote.

Browser isolation headers

nosniff, X-Frame-Options DENY, a same-origin opener policy, a same-origin referrer policy, and a permissions policy that turns off camera, microphone, location, payment, and USB access.

API responses

API responses are marked no-store. Production errors return a generic message, and the health check returns only a status flag.

Password length

New passwords must be at least 15 characters.

Security contact

An RFC 9116 security.txt at /.well-known/security.txt points to private vulnerability reporting.

Accounts, storage, and audit records

These controls were confirmed by source review in October 2026. Where a control is also live in the production database, the card says so.

Password storage

Passwords are hashed with Argon2id. Sign-in compares against a dummy hash when an account does not exist, so response time does not reveal which emails are registered.

Source reviewed

Sessions

Session tokens are 256-bit random values stored only as SHA-256 hashes. The cookie is HttpOnly, Secure, and SameSite=Lax. Sessions last up to seven days and are revoked on password change, password reset, and account deactivation.

Source reviewed

Single sign-on

OpenID Connect sign-in can be enabled per deployment and requires multi-factor authentication by default. truenote.org uses password sign-in today.

Source reviewed; SSO tests passed

File storage

Uploaded files are kept in a private bucket and read only through the server. Truenote issues no public or pre-signed file links.

Source reviewed

Hash-chained security events

Sign-ins and administrative and document changes made through the API are written through a database function that links each event to the one before it with a SHA-256 hash. Background steps such as parsing and automatic activation are not yet recorded as security events.

Function present in production, October 2026

SIEM delivery

A signed, retrying delivery queue for sending security events to a customer's SIEM is written and unit-tested. It is not connected on truenote.org today.

Unit tests passed; not deployed

Security delivery checks

The hosted workflow runs these checks on every pull request, every push to main, and weekly. All passed on the main branch on October 9, 2026.

Type checking and production build

Workspace TypeScript checks and the frontend production build.

Automated test suites

Frontend, API, and security-script test suites.

Secret scanning

Gitleaks scans each pull request and push for committed credentials.

Dependency audit and SBOM

The build fails on high or critical advisories in production dependencies, and each run generates a CycloneDX software bill of materials.

CodeQL analysis

CodeQL runs its security-extended JavaScript and TypeScript queries. Its findings are tracked in a triage register in the repository.

Protected main branch

Changes reach main only through pull requests, and the four checks above must pass before merge. Repository administrators can override the checks on a pull request.

Security evidence integrity

Machine checks validate evidence links, identifiers, hashes, and required security records.
