Plain-language context

PCI DSS includes secure-software requirements for systems that are inside, or can affect, a cardholder data environment. For an application such as Truenote, that means disciplined software development, vulnerability detection, protection against common web attacks, and controlled releases. This page lists the safeguards Truenote has completed and tested, how it handles payment-card data, and what stays with the customer.

Payment-card data in Truenote

Truenote answers questions from a customer's own procedures and policies. It is not designed to store, process, or transmit cardholder data and needs none to work. It detects card numbers written as 13 to 19 digits, separated only by spaces or hyphens, that pass the Luhn check. Detection is pattern-based: a card number written another way, such as split across lines, is not caught. The checks run where text enters or leaves the system:

Questions

A question or conversation history containing a card number is rejected before it is stored or sent to any provider.

Uploaded documents

A document containing a card number is quarantined after parsing and never becomes searchable.

AI provider requests

Card numbers are redacted from text before it is sent for embedding, reranking, or answer generation.

Answers

A generated answer containing a card number is refused instead of shown.

Limits: an uploaded file is stored and sent to the document parser before the card-number check runs. Removing a document retires it and keeps the stored file; only a separate super-user purge deletes the file, and the purge does not ask the document parser to delete its copy, which follows the parser's own retention settings. Personal notes and label names are not screened yet. Customers should keep cardholder data out of every document and field they put into Truenote.

Scope and customer responsibilities

Assessment status

Truenote has not completed a PCI DSS assessment and holds no Attestation of Compliance or Report on Compliance. Whether Truenote falls within a customer's assessment scope depends on how the customer connects it to their environment; the customer's assessor makes that determination.

Customers that use Truenote alongside a cardholder data environment should:

  • Keep cardholder data out of uploaded documents, questions, notes, and labels.
  • Keep Truenote outside the cardholder data environment, with network segmentation their assessor accepts.
  • Turn on single sign-on through their own identity provider with multi-factor authentication, and manage staff accounts there.
  • Review the service providers listed on the Security page and include Truenote in their own risk and scope assessment.

Completed safeguards

Each item below is backed by implementation and a passed repository test, or by a check of the live service on October 9, 2026. Where part of a safeguard is not active on truenote.org, the card says so.

01

Threat-driven testing

A threat model maps application, AI-provider, authorization, data, hosting, and PCI-impact threats to controls and tests. It was updated in October 2026 for the move to Railway. Negative tests check that each boundary fails closed.

02

Pre-provider data screening

Questions and conversation history containing deterministic high-risk data are blocked before storage. Text sent to embedding, reranking, answer, and utility-model providers is redacted first.

03

Model-output screening

Sensitive generated text is blocked before a normal answer is returned. Missing or invalid citations also produce a refusal.

04

Server-side access boundaries

Program and classification limits are applied before retrieval and checked again before protected content can reach generation or citation lookup.

05

Controlled content activation

File-type, file-signature, EICAR, sensitive-data, source, parsing, lifecycle, and role checks must pass before knowledge content becomes available. An external malware scanner can be connected; none is enabled on truenote.org today.

06

Web application protection

HTTPS is enforced with a two-year Strict-Transport-Security header. A nonce-based Content Security Policy requires Trusted Types and blocks framing. Browser requests that change data are rejected unless they come from Truenote's own origin.

07

Account security

Passwords are hashed with Argon2id and must be at least 15 characters. Session tokens are stored only as hashes and sent in HttpOnly, Secure cookies. Single sign-on with multi-factor authentication is available per deployment; truenote.org uses password sign-in today.

08

Automated security analysis

Every pull request runs CodeQL, secret scanning, a production dependency audit, software bill of materials generation, type checks, a frontend build, and unit tests. Four required checks must pass before a change reaches main; repository administrators can override them on a pull request.

09

Hash-chained security events

Security events from sign-ins and API changes are written through a database function that links each event to the one before it with a SHA-256 hash. SIEM delivery code (signed payloads, retry leases, backoff, dead-letter handling) is written and unit-tested; it is not connected on truenote.org today.

Checks that passed

These results verify the repository implementation and its documented evidence package.

Access isolation

Unit tests of the authorization checks used by retrieval, citations, and document reads denied cross-program and above-clearance access.

AI input boundary

Portable tests captured provider payloads and confirmed deterministic redaction before supported provider calls.

Citation and refusal rules

Tests rejected missing, malformed, unknown, and out-of-range citations and refused sensitive model output.

Browser request defense

Tests accepted trusted same-origin mutations and rejected foreign, opaque, malformed, cross-site, and sibling-origin requests.

Audit delivery logic

Tests passed signed delivery, retry scheduling, completion, and dead-letter handling. The lease-fenced database functions were checked by content.

Security delivery pipeline

The October 9, 2026 run on main passed type checking, the frontend production build, unit tests, secret scan, dependency audit and SBOM, and CodeQL analysis. Open CodeQL findings are tracked in a triage register.
